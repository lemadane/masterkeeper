# Resolution Summary - Durability, Recovery, and Schema Validation Issues (2026-08-04)

This document summarizes the changes implemented to address functional issues, concurrency anomalies, type registries, and documentation gaps in MasterKeeper.

---

## 1. Concurrency and Transaction Fixes

### Issue 1: Bounded & Context-Driven Transaction Locks (Anomaly 1 & 2)
- **Fix**: Replaced the thread-stack inspection heuristic (`isGoroutineBlocked`) with a robust context-aware locking mechanism:
  - Changed `writeLock` from `sync.Mutex` to `chan struct{}` (initialized with 1 token).
  - Implemented `lock(ctx)` and `unlock()` helpers using `select` to allow channel-based lock acquisition. If the context is canceled or reaches its timeout while waiting for the lock, `lock(ctx)` returns the context error immediately.
  - Added configurable `TransactionWaitTimeout time.Duration` option (defaulting to 30 seconds).
  - Refactored `Transaction()` to use a bounded timeout context *only while acquiring the writer lock*, preventing callback execution from being limited after lock acquisition. If lock acquisition times out, `TransactionWaitTimeoutError` (wrapping `context.DeadlineExceeded`) is returned.
  - Retained same-goroutine nesting checks via `activeGoroutineID` and context-propagated nesting checks via `txContextKey` inside `TransactionContext()`.

## 2. Durability and Recovery Fixes

### Issue 2: Final WAL Checksum Corruption Ignored
- **Fix**: Detection of a checksum mismatch in `ReadAllRecords()` in `wal.go` is now treated as a hard corruption error under all circumstances, removing the assumption that mismatches at the end of the file are safe truncated/torn writes.

### Issue 3: WAL Commit Write Ordering
- **Fix**: Enforced strict write ordering in transaction commit. The write path now:
  1. Writes and syncs the transaction mutations (`OpBeginTransaction` and operational records) to the WAL.
  2. Performs the table database file appends and syncs the table files.
  3. Writes and syncs the transaction final marker (`OpCommitTransaction` or `OpRollbackTransaction`) to the WAL.

### Issue 4: Staged & Atomic Snapshot Restoration
- **Fix**: Refactored `readSnapshot()` in `db.go` to parse the complete snapshot metadata and records into memory and perform dry-run decoding and count bounds-checking first. Active `.db` files are temporarily renamed to `.db.old` before reconstruction. If the restore succeeds, `.db.old` files are deleted. If any failure occurs, a deferred rollback restores the original `.db` files, preventing corruption of active storage files.

### Issue 5: Bounds-Checking on Lengths and Counts
- **Fix**: Added strict bounds-checking on lengths and counts read from disk:
  - WAL payload length validated to be \ge 0, \le 64MB, and \le remaining file size (gracefully handled as a safe torn write if it exceeds remaining bytes).
  - String length restricted to \le 16MB in `readString()`.
  - Snapshot count metadata (`tableCount` \le 10000, `indexCount` \le 1000, `recordCount` \ge 0, and `recordLength` \le 64MB) are validated.
  - Record pointer sizes and offsets are validated to be non-negative in `ReadRecord()`.

### Issue 6: Legacy Snapshot Magic Compatibility
- **Fix**: Extended snapshot magic verification to accept both the current magic `0x524d524d` (RMRM) and the legacy magic `0x524d534e` (RMSN) for backward compatibility.

### Issue 7: Unknown WAL Operation Rejection
- **Fix**: Enforced strict validation of WAL operation type bytes:
  - Inside `ReadAllRecords()` in `wal.go`, type bytes exceeding the range of valid constants (>11) are rejected immediately.
  - Inside the recovery loop in `db.go`, a `default` case was added to the switch statement to explicitly return a corruption error if an unknown operation is encountered.

## 3. Schema and Validation Fixes

### Issue 8: Generic ID Pointer Type Validation
- **Fix**: Updated `validateSchema()` to reject pointer types for the generic `ID` constraint with `IncompatibleTypesError`, enforcing exact type compatibility to prevent runtime interface type casting panics.

### Issue 9: Pointer Entity Type Validation
- **Fix**: Updated `validateSchema()` to reject pointer types for the entity generic parameter `T` with `IncompatibleTypesError`, avoiding reflection crashes when accessing fields on pointers.

### Issue 10: Nil Interface Entity Validation
- **Fix**: Added safety checks to `validateSchema()` in `db.go` to reject `nil` reflection types (which occurs when generic types like `any` or other interfaces are passed), returning `IncompatibleTypesError` instead of panicking.

### Issue 11: Nil Type Registration (options.RegisterTypes)
- **Fix**: Added a guard `if value == nil { return }` at the beginning of `RegisterType()` to safely handle registering `nil` types.

### Issue 12: Query Comparison Numeric Coercion
- **Fix**: Enhanced `compareValues()` in `state.go` with type-coercion helpers. Integers (`int8`, `int16`, `int32`, `int64`, `int`) and floats (`float32`, `float64`) are normalized to `int64` and `float64` respectively to preserve numerical precision and ordering during comparisons.

### Issue 13: Non-Comparable Index Keys
- **Fix**: Introduced `canonicalizeKey()` in `state.go` to translate non-comparable values (such as `[]byte`) to comparable string representations (`string([]byte)`) for map lookups and unique check constraints.

## 4. Documentation Fixes

### Issue 14: README API Outdated Reference
- **Fix**: Updated `README.md` to reference `masterkeeper.Equal` instead of the outdated `masterkeeper.Eq`.
- **Fix**: Documented safety guidelines and concurrency rules for `Transaction()` and `TransactionContext()`.
